# 视觉模型直连看图：请求体加一个 vision_capable

## Context

服务端 `apply_vision_policy` 会把每张图**无条件**转成文字：先走 VL 描述（3.4s），
失败再走本地 OCR，都失败给「看不到」占位。这个设计的前提是「对话模型只能吃文本」
—— 对 `spark-x2.6` 成立，对 `doubao-seed-2-1-pro` 这类 VLM 不成立。

后果是：用户选了能看图的模型，服务端还是先花 3.4s 让另一个模型把图描述一遍，
对话模型看到的是**转述**而不是原图 —— 颜色、图标形状、布局关系全丢了，
问「这个按钮是蓝的还是灰的」得不到准确答案，还白付一次视觉调用的钱。

谁该决定「这个模型能不能看图」？只有客户端知道：模型清单
（`ModelCatalog`）就在客户端，`Vision` 标记是现成的。

## Decision

客户端在请求体里加一个私有字段：

```json
{ "model": "doubao-seed-2-1-pro-260915", "vision_capable": true, ... }
```

- 只在 `ModelCatalog.Find(settings.Model)?.Vision == true` 时发；纯文本模型**不发这个字段**，
  行为与改动前完全一致（服务端照旧转文本）。
- 服务端把它加进 `_DROP_FIELDS`（不转发给上游），`apply_vision_policy(body, pass_through)`
  在 `VISION_MODE=auto` 时直接原样返回图片块，并打一行
  `vision: 直连透传 N 张图（对话模型自己看，跳过 VL/OCR）`。
- **显式强制档优先**：`VISION_MODE` 被人工设成 `ocr` / `vl` / `strip` 时不理会这个标记 ——
  那是排障用的，人的意图高于客户端的自动判断。
- 服务端不维护「哪个 id 能看图」的表：两份清单必然漂移，而客户端已经有一份。

## Considered Options

- **服务端按模型 id 前缀猜**（`doubao-seed-2-1-` 就是 VLM）：实现最省事，但前缀和能力不对应
  —— 同一前缀下有纯文本型号，猜错就会把图片发给看不见它的模型。
- **服务端存一份 Vision id 白名单**：准确，但和 `ModelCatalog` 双写，加模型要改两处。
- **客户端直连方舟，绕开服务端**：要重写一遍 SSE + 工具回环，密钥还会落到客户端。
- **总是直连**（`VISION_MODE=pass`）：纯文本模型会收到它看不见的图片块，
  实测 spark-x2.6 对图片是静默丢弃然后反问用户「屏幕上是什么」，比报错更糟。

## Consequences

- 协议多了一个**可选**字段。点点从来不发它，所以点点那条链路一个字节都没变；
  老版本客户端也不发，行为退回「服务端转文本」。
- 实测（同一张 1280×720 截图，同一句问题）：
  - VLM 直连：首字 1957ms / 总 2870ms，且能引用具体坐标做标注
  - 纯文本 + VL 转述：首字 4898ms / 总 5054ms
  省掉的就是那 3.4s 的 VL 描述。
- 直连之后 OCR / VL 的日志一条都不会出现，排障时看 `vision: 直连透传 N 张图`
  这一行确认「图到底有没有发出去」。
- 视觉模型现在拿到的是原图，`VISION_TIMEOUT`、OCR 缓存这些都不再作用于这类回合。
- 风险面：如果 `ModelCatalog` 把一个纯文本模型错标成 `Vision=true`，图片会直接发给它，
  表现是「模型说看不到」而不是报错。`ModelCatalogTests` 钉住了分组标记，
  `ChatRequestBodyTests` 钉住了「标记跟清单走」。
